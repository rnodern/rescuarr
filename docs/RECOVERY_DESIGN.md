# Rescuarr recovery and learning design

Rescuarr turns a stalled download into a case with a specific diagnosis, a next step, and a verified result. The normal path is unattended. It waits while the downloader is still working, attempts a supported import when the original download can satisfy the request, and asks Sonarr or Radarr to find another release when the original has conclusively failed. Cases requiring judgment stay visible with the evidence and the available actions. The upstream application owns monitoring, library matching, release eligibility, quality profiles, custom format scoring, imports, and downloads.

## Operating policy

| Mode | Authority |
| --- | --- |
| Observe | Collect evidence, diagnose, predict eligible plans and deliver configured notifications. The engine issues no Arr writes in this mode. |
| Assist | Expose certified actions for explicit approval. Approval applies once to a single evaluated plan. A changed target, scope or prerequisite requires a fresh plan and approval. |
| Autonomous | Execute action classes the administrator enabled individually for this instance, within their configured scope and budgets. Other certified actions can still be proposed for review. |

The effective permission is the strictest of the global mode, instance mode, action permission, instance and dependency health, adapter contract, and live preconditions. A manual approval can supply the authorization required by Assist or select a permitted alternative. It cannot authorize an unsupported external effect, stale target, unresolved overlap or deletion beyond the defined action contract. Rule settings may match explicit instance, protocol, tag, root, media type or download-client scope. Evaluate hard safety gates before operator exceptions. Apply narrower scope restrictions and any explicit deny before enabling the action. Display the active policy, scope and effect before an operator enables a write. An emergency stop is persistent and affects undispatched writes only. It preserves the reconciliation of earlier writes and shows which upstream actions may still complete.

## 1. Domain model

| Entity | Identity and lifecycle |
| --- | --- |
| Instance | Internal UUID, Arr product, installation identity when available, connection revision, and configuration epoch. Changing an address or credentials requires revalidation. A different installation at an existing address starts a new identity and cannot inherit outstanding write authority. |
| Observation | Timestamped, typed fact with source, scope, source record identity, adapter/schema version, fetch time, source time if present, snapshot generation, and freshness. Values distinguish known, missing, unknown, stale, and unsupported. |
| Job | A download owned by an instance. Match primarily on the Arr instance and stable download ID, with a client identity or namespace where the adapter requires it. An optional client lookup is joined only with a confirmed client mapping and exact ID. Reused IDs require a new job generation. |
| Job member | One upstream queue record attached to a job. A pack can have multiple members. Queue row IDs are handles for particular reads or writes, with the associated snapshot generation, job identity, and target mapping. |
| Target | Sonarr episode ID with series ID or Radarr movie ID, scoped to its instance and identity epoch. A case stores a sorted target set and tracks verification per target. Multiple jobs can contend for one target. |
| Case | The story of one job generation and its targets. Captures current diagnosis, history, incident links, decisions, operations, and per-target outcomes. A verified replacement is linked as a new job case rather than overwriting the original job identity. |
| Diagnosis | Versioned primary reason, contributing reasons, facts, uncertainty, confidence class, and next check. A case may change diagnosis as stronger facts arrive. |
| Decision | Immutable evaluation of a specific observation revision against a policy revision, adapter capabilities, budgets, and learned pattern revision. Contains candidate actions and the grounds for permitting or rejecting each. |
| Action intent | An immutable approved action with bound job and target identities, preconditions, expected effects, operation key, approval actor or policy revision, expiry, and reconciliation plan. |
| Action attempt | One dispatch and its evidence. Records request class, upstream result or uncertainty, timestamps, and readbacks. Never stores credentials or raw responses by default. |
| Incident | A shared failure within an instance, downloader, service, root path, or verified storage scope. Stores affected cases, trip condition, pause reason, and recovery checks. |
| Outcome | Evidence-backed result per intended effect and target. Separate from the action's HTTP result and the case's current state. |
| Pattern | A local, versioned record that associates a typed evidence fingerprint with a previously verified diagnosis or permitted treatment. Retains sample counts, exclusions, verification method, expiry, and disable history. |

### Correlation and ownership

1. Bind Arr records to their instance UUID and verify the instance's installation identity on reconnect. A suspected rollback or restored database with reused IDs suspends writes until the instance is revalidated.
2. Group queue members by stable download identity. If the adapter can prove that the ID is scoped to a client, include that namespace. Preserve the original identifier as an opaque value and only normalize it according to that adapter's documented equality rules. A missing download ID yields an observation-only case.
3. Resolve targets through exact queue relationships or grab history tied to that job. Use library metadata to confirm target IDs, monitoring, desired profile and current files. Filename, release title, indexer, and timestamps can explain a match or surface a candidate for review. A title or timestamp alone cannot establish job ownership or target identity.
4. Identify the originating release using explicit provenance from Arr where available, including grab history ID, source indexer ID, release GUID, protocol and edition or version attributes. Use client records to supplement job state and diagnostics. Two same-named grabs can have distinct provenance. A missing source prevents actions that require precise release attribution.
5. Build the complete target set before planning a job-level action. Consider unknown episode mappings, multiple editions, multi-episode files, new queue members, and competing jobs on other configured instances that share a client. A potentially shared job or a partially observed pack is ineligible for automatic removal. A stable job can be displayed while individual targets remain unconfirmed.
6. Detect job ID reuse using confirmed conflicts such as a different client mapping or exact provenance. Preserve the old case, increment its generation, and revoke old intents. With insufficient evidence, hold the action and show the conflict.

### Freshness and confidence

- An observation has its own age. A successful poll of system status does not refresh queue, library, capacity, or history observations. A failed or partial fetch preserves the last visible values with an explicit stale marker.
- A coherent queue read includes all required pages and sees no incompatible pagination changes. If rows move across pages, repeat within a bounded read budget. Until then a missing row has no evidentiary value. A job missing in two successful coherent scans is eligible for reconciliation, with a targeted lookup wherever available.
- Typical defaults are 10 minutes since first confirmed completion and two consecutive coherent, consistent observations at least 30 seconds apart. For a job discovered already complete, the grace clock starts from first observation unless reliable upstream timestamps and post-processing state establish the elapsed time. An explicit active unpack or import always extends the hold.
- Before dispatch, re-read the exact job, current target library facts, and all hard gates. Require a current snapshot within 60 seconds for job and library facts and within 5 minutes for any capacity facts on the operation's relevant volumes. An adapter can require fresher facts or stronger checks for a specific release.
- Use monotonic elapsed time for in-process durations and UTC for persisted scheduling and audit. On resume after long sleep, backward clock change, or inability to establish an elapsed interval, expire action preflights and refresh evidence before any further writes.
- Facts drawn from one Arr payload and a rephrasing of that same payload count as one source. Independent support means a separate diagnostic signal with a distinct failure mechanism, such as an exact SABnzbd job error corroborating Arr history or a constrained probe corroborating a file rejection.
- Confidence classes are `verified` for all required typed facts and independent checks, `probable` for a known reason with unresolved dependencies, and `unknown` for incomplete or conflicting evidence. Historical success may change evaluation order and suggested guidance. It cannot raise evidence to verified.

### Desired quality and release selection

Capture the intent associated with the grab and resolve current intent again before any write. Include monitored target and parent, current profile ID and revision, ordered quality groups, cutoff and upgrade setting, applicable format criteria and minimum score, known language and edition constraints, current library file identity and known quality, and context for any quality- or format-driven upgrade. Parse only fields whose semantics the adapter certifies. A missing field required to resolve a conflict yields unknown intent. Display source profile and its age beside any recommendation. A transient metadata fetch failure never replaces the profile with defaults.

The engine recognizes four different needs for each target. A missing file needs an eligible first import. An existing file below the quality or custom-format target can have a permitted upgrade. A file at the active target can satisfy the request. An explicit unmonitor or withdrawal ends automatic pursuit. These are derived from Arr state and compatible current import decisions. The engine does not reimplement a release-ranking algorithm or compare numeric quality IDs as though they were an ordered scale. A higher resolution, HDR, different language, special edition, quality group tie, or manually selected candidate may be undesirable under the current upstream rules.

For an upgrade case, a present file is the baseline and remains the fallback until Arr reports the intended upgrade. If another acceptable job is still queued, watch it before searching. If no compatible Arr quality comparison is available, leave current-file satisfaction or upgrade impact as unknown and require an exact current Arr proposal or native handoff. A recovery action never implicitly changes monitoring, cutoff, allowed qualities, format scores, language, custom formats, editions, or the upstream release selection order. An operator can change those preferences in Arr and the engine will rebuild plans from the updated facts.

## 2. Case and action state machines

A case keeps a single current workflow state and append-only state transitions with trigger, actor, and evidence version. Per-target outcomes, pending dispatches, upstream states and incident links are independent projections. A queue record can disappear without producing a successful case.

| Case state | Entry and permitted transitions |
| --- | --- |
| `observed` | A job or actionable history event is discovered. Re-read and enter `waiting`, `assessing`, or `held`. |
| `waiting` | Ordinary progress, post-processing, upstream import, grace period, eventual consistency, scheduled cooldown, or completion of another owned operation. Set a reason and next eligibility time. Re-enter `assessing` on the next valid trigger. |
| `assessing` | Evaluate the newest coherent facts and run a bounded number of read-only probes. Enter `proposed`, `ready`, `held`, `waiting`, or `closed`. |
| `proposed` | A plan exists and requires an operator decision. Expiry or any change to material preconditions returns it to assessment. Decline records a decision and holds that plan until evidence or policy changes. |
| `ready` | Policy or operator authorized a specific intent. Persist the intent before reservation or dispatch. A failed preflight invalidates authorization and returns the case to assessment or hold. |
| `executing` | Rescuarr has reserved the applicable scopes and sent, or may have sent, a write. Completion of transport moves the case to `verifying` or `held` if the adapter proved rejection before any mutation. |
| `verifying` | Read the authoritative upstream effects, separately for each member of a composite operation. Resolved outcomes progress to `assessing`, `waiting_replacement`, or `closed`. Unresolved or inconsistent effects move to `held`. |
| `waiting_replacement` | A replacement workflow was selected. Track acknowledgement, search result where exposed, and new grabs. Link a new job if one appears and progress to `closed` only when the target outcome is verified or explicitly exhausted. |
| `held` | An incident, ambiguity, budget, missing capability, uncertain write, expired approval or explicit pause blocks further actions. Recovery checks run on schedule or on request. Clearing a hold returns the case to assessment. |
| `closed` | Result is recorded as imported, already satisfied, replaced and verified, accepted partial, exhausted, withdrawn, externally resolved with evidence, or disappeared without proof. Reappearance after closure starts a new job generation only if identity has genuinely changed. A reopened same-job case retains its original budgets and action history. |

Each intent progresses through `planned`, `authorized`, `reserved`, `sending`, then `acknowledged`, `rejected_before_effect`, or `uncertain`. Any acknowledged or uncertain attempt must reconcile to `verified_effect`, `verified_partial`, `verified_no_effect`, or `unresolved`. Timeout, connection reset, unexpected response, and cancellation during a send are uncertain by default. An acknowledged write with no verified effect consumes its action budget. A verified no-effect result requires positive evidence defined by the capability contract.

A case's resolved outcome distinguishes Arr importing the original release, another actor importing it, a verified prior library file already satisfying the intent, a replacement import, and partial success. Keep separate result fields for original queue removal, client job removal, client data removal, release blocklisting, search dispatch, replacement grab, and final library satisfaction. Record any effect as unknown when it is outside the exposed API and probe capabilities. A cleanup-only action never earns a recovery success.

## 3. Diagnostic precedence and treatment

Evaluate hard gates first. Global pause, an unsupported write contract, conflicting job ownership, failed upstream identity validation, stale evidence, an open applicable incident, budget exhaustion or an unresolved overlapping attempt can prevent writes regardless of diagnosis. Diagnostics still run where useful. Within a case, pick the highest-priority reason supported by current evidence and retain contributing reasons. A precise signature may add detail beneath an upstream generic warning.

| Priority and reason | Required evidence | Normal disposition |
| --- | --- | --- |
| 10 `upstream_unavailable` / `authentication_failed` / `contract_changed` | Transport, authentication, adapter schema, or upstream identity failure | Hold affected writes. Retry bounded read-only health checks. Surface the exact service and affected capabilities. |
| 20 `ownership_conflict` / `target_ambiguous` / `unknown_provenance` | Missing or contradictory exact identity, multiple mappings, shared client reference, or incomplete target set | Show candidate mappings and their evidence. Allow only actions whose own preconditions can be independently proven, with explicit user approval where appropriate. |
| 30 `root_path_unavailable` / `path_mapping_missing` / `permission_denied` / `capacity_low` | Typed health or path facts, repeated corroborated errors, trustworthy capacity below configured floor, or known path mapping fault | Group affected cases into an incident. Pause relevant imports and replacement activity. Explain which service needs which path and what to check. Re-evaluate preserved jobs after recovery. |
| 40 `download_active` / `post_processing` / `arr_import_in_progress` / `completion_grace` | Coherent upstream activity or time within the grace interval | Wait for an authoritative state change. An overlong processing state becomes a persistent exception with elapsed time and scope. |
| 50 `target_withdrawn` / `request_changed` | Unmonitored, deleted, moved, or materially changed target or profile | Recompute intent. Hold upstream writes when target IDs or policy changed. Declining further recovery can close the case without deletion. |
| 60 `already_satisfied` | Current mapped library files meet the intended upstream quality and format criteria for every target, and lack of pending eligible upgrade is confirmed if relevant | Close recovery. Offer independent queue housekeeping only where its semantics and preservation of client data are verified. Respect seeding and shared-job ownership. |
| 70 `safe_import_candidate` | Stable completed job, unique file-to-target mapping, clean import proposal within applicable Arr rules and suitable evidence for each selected file | Propose or run supported Arr import. Verify every intended library file and identity before considering downstream cleanup. |
| 80 `partially_recoverable_pack` | Known viable members and known unsupported, ambiguous, corrupt, or absent members | Present pack membership and a per-file action. A certified subset import may proceed under policy if it preserves unselected members. Hold pack cleanup and reassess missing targets after verified imports. |
| 90 `quality_or_format_rejected` | Upstream reports a release, file, format, edition, language, size or quality conflict with current requirements | Respect Arr's current rules. If the library is already satisfied, take the corresponding disposition. For genuine unsatisfied targets show the rejection and consider a separately eligible replacement. Avoid automatic score overrides or profile edits. |
| 100 `archive_unresolved` / `password_required` / `sample_only` / `file_unreadable` / `download_failed` | Exact typed reason with a verified job and evidence of the relevant terminal state | Wait if recovery, unpacking, or storage checks remain outstanding. If irreparable failure and independent corroboration are established, evaluate precise replacement eligibility. |
| 110 `stalled_unknown` / `unsupported_payload` | Persistent symptoms without sufficient typed proof, or unknown upstream state/structure | Retain the case. Gather the next useful read-only evidence and surface the exception after its wait budget. |

Map upstream status and structured codes first. Versioned, anchored text matchers may map known warning forms to a diagnosis when structured reasons are unavailable. Matchers cover localized signatures explicitly, use bounded input length and literal or linear-time parsing, and retain an unknown fallback. A raw log line, user-defined regex, unsupported locale or generic manual-intervention warning can never confer write authority. Store concise redacted evidence references and show a source link for detailed inspection.

### Candidate ordering and stop conditions

After a complete, current assessment, select the first eligible disposition in this order. Observe an active upstream operation, hold a systemic fault, verify an already-satisfied target, rescue the complete original job, rescue a certified subset, retire a conclusively failed release and let Arr replace it, or hold for manual resolution. A newly available safe recovery path invalidates a previously proposed deletion. A more urgent action can advance only when each previous applicable branch has a recorded disqualifier. Ties among cases use due time, then discovery order, then stable case ID. This makes budgets and replay reproducible.

Case readiness includes a finite next check and an owner for each dependency. A job can stay parked while waiting for evidence or operator intervention with no hot polling. Examples include a missing root mapping, revoked API key, unsupported version, pending queue ownership, or storage floor hold. A scheduled full read, material case change, service health recovery, or explicit retry can re-enter the assessment queue. Repeating the same failure text without new facts cannot reopen a write attempt.

### Recover the existing download

- Request Arr's current manual import proposal for the exact job and paths when the adapter provides a validated read contract. Show candidate file, media identity, rejection reasons, selected import behavior and ownership. Retry a stale proposal by rebuilding it. Never dispatch old proposal payloads.
- Establish target identity from exact Arr evidence and unique file mapping. Verify each path is beneath a configured or Arr-certified import root on the Arr host. Local accessibility is optional. If using a local read-only mount, require explicit namespace mapping, containment checks, and regular-file verification. A constrained optional media probe can supply duration or stream evidence within a size, runtime and concurrency budget. Media or archive contents supply facts only and never become executable or interpolated shell input.
- Confirm stable files, completion, and acceptable upstream import policy. Choose a source-preserving mode only when the adapter has verified semantics for that installation and protocol. Observe existing Arr imports and reconcile them before initiating a second one. Sample classification, ambiguous media identities, format or score overrides, multiple plausible edition matches, active seed jobs with unknown effects, and file collisions require review or hold.
- A source-preserving import contract covers the command, upstream tracked-folder housekeeping and normal completed-download handling. A copy-mode request alone cannot establish preservation. For a partial pack, shared job, or seeding torrent, require certification that the selected files, unselected files, parent folder and client job retain the expected state. Otherwise keep the preview and link to the owning application's native workflow. [Sonarr tracked manual import source](https://github.com/Sonarr/Sonarr/blob/develop/src/NzbDrone.Core/MediaFiles/EpisodeImport/Manual/ManualImportService.cs) · [Radarr tracked manual import source](https://github.com/Radarr/Radarr/blob/develop/src/NzbDrone.Core/MediaFiles/MovieImport/Manual/ManualImportService.cs)
- An import affecting a current library file is automatically eligible only when Arr's current rules explicitly accept the upgrade and the certified contract preserves desired quality and target association. Use per-target exclusivity and fresh library checks. An automatic import never bypasses an upstream rejection through a broad force setting.
- Verify the reported command result when available, plus changed library state and the expected media association for every target. Where possible correlate history to the job, command or imported file. If a different actor satisfies the target during the attempt, record external resolution. Only strong causality feeds learning.
- Verify media identity using Arr target and candidate association. Filename patterns and duration supply supporting evidence. For Sonarr, handle specials, absolute numbering, scene mapping and multi-episode files through certified Arr mappings. For Radarr, hold ambiguous remakes, alternate cuts, and duplicate movie IDs across independent instances. A valid media stream alone confirms readability.
- If manual import requires direct filesystem moves, archive extraction, permission changes, access to remote paths unavailable to Arr, or unsupported Arr parameters, surface those dependencies and offer safe guidance. Operators can correct underlying configuration in the owning service and trigger reassessment.

### Abandon a bad release and request a replacement

Replacement requires an eligible monitored target, unmet requirements, no competing acceptable grab, no unresolved write, stable exact release ownership, and a known terminal reason. Link this action to an intent lineage for the target set. Prefer retaining files when a verified Arr route can blocklist and retire a release without a physical delete. Where no such route is verified, present an operator proposal only for certified supported effects.

Automatic physical removal is restricted to a failed, dedicated Usenet job where all targets and the exact release are known, a typed terminal failure is corroborated independently, Arr has not imported anything usable from the job, no target or another instance is using it, no downstream process is active, and a certified adapter/client combination exposes known delete semantics. A user must enable this action explicitly. Default manual approval specifies the affected job, members, release, side effects, and source preservation status. Automatic removal is disabled for torrents, shared jobs and partly salvageable jobs. An unknown protocol is also ineligible. Torrent actions respect seeding, share ratios and client/category ownership. Automated operations never remove library files or delete a local filesystem path directly.

Treat Arr's combined queue-removal and blocklist request as potentially partial. The action can affect the download client before persisting a blocklist entry. A missing client job, vanished queue record, failed history entry and matching blocklist entry are separate observations. Before submitting a combined action, verify exact grabbed-history association wherever the integration requires it. Unknown delete or blocklist status suspends the dependent explicit search. Where upstream cannot expose physical data removal, show that effect as unknown even if it confirms retirement of the queue and client job. [Sonarr queue controller](https://github.com/Sonarr/Sonarr/blob/develop/src/Sonarr.Api.V3/Queue/QueueController.cs) · [Radarr queue controller](https://github.com/Radarr/Radarr/blob/develop/src/Radarr.Api.V3/Queue/QueueController.cs)

Select one search authority per operation before dispatch:

1. When the version-specific Arr workflow can suppress its own redownload and a targeted search is supported, disable implicit search using the certified contract. Verify the requested blocklist and queue/client effects, then re-read monitoring, profile, active grabs, storage gates, and retry budget. Dispatch only an exact scoped search for the still-unsatisfied targets.
2. When implicit Arr search is part of a verified contract and cannot be reliably suppressed, treat it as the operation's sole search authority. Observe Arr history and active grabs. Do not issue another search for the same action lineage.
3. If neither search path can be verified, hold for operator action. If removal, blocklisting, search, or library effects are uncertain or partial, record each separately and reconcile. An Arr command accepted or marked complete is distinct from an actual replacement grab.

Target sets from overlapping season packs are evaluated episode by episode. Prefer the smallest supported search scope. Never escalate an episode case to a series-wide or library-wide search. A targeted search may produce another season pack under Arr's rules. Its job case links back to the affected target lineage and cannot reset retry budgets. A stable original remains visible when only a subset is fixed. If duplicate grabs reappear from several indexers, upstream provenance and profile still govern. Rescuarr can show recurrence evidence without banning an entire indexer or broadening the blocklist.

## 4. Durable execution, retries and incidents

### Reserve, write, verify

1. Generate an operation key from instance and job generation, normalized action type, stable release identity when required, sorted target IDs and material plan parameters. Bind approvals to the exact decision hash including policy, capabilities and prerequisite evidence revisions. Store a new sequence only for a materially new, eligible action.
2. Within a short database transaction, reserve the job and affected targets, decrement the configured attempt budget, and persist the intent and audit record. A unique active operation constraint and target locks exclude overlapping writes. Retain locks across restarts until uncertainty resolves. No network requests run inside the transaction.
3. Revalidate all preconditions close to dispatch and store the specific Arr handles used. If invalid, cancel before send and release the reservation. A reservation proven never dispatched can release its attempt charge. A process crash after committing the `sending` marker always enters reconciliation.
4. Dispatch once with bounded timeout, automatic redirect following disabled, and no transport-layer retry for mutations. Arr or the client may act between reads. Pass any supported request preconditions, minimize that interval, and stop on conflicting state instead of trying a different row ID blindly.
5. Persist response or uncertainty, then schedule readbacks. Reconcile upstream queue, history, command state, library and blocklist only where relevant. If another system wins the race, record externally verified target satisfaction where evidenced and leave Rescuarr's effect unknown unless separately proven. Once all verification completes, commit final outcomes and any notification outbox entries together.
6. After restart, reconcile every outstanding intent before permitting writes in its scope. If a database restore could omit newer intents, start in Observe and perform a targeted upstream reconciliation before an operator re-enables mutations. A second app process must fail to acquire the same state directory lock. Separately deployed instances need distinct ownership scopes or a single designated mutator.

### Default pacing and limits

| Limit | Proposed default |
| --- | --- |
| Active writes | One per Arr instance and one per shared client, with target and job exclusivity. Global concurrency of two. |
| Import | One dispatch for the original job with a given material evidence revision. Permit a second only after a verified no-effect result or changed source facts and a fresh eligible decision. Absolute maximum two per original job in 24 hours. |
| Replacement | Two cycles per target in a rolling seven days, using the most restrictive remaining budget in a set. Minimum 60 minutes between cycles. A different release or new case cannot reset the target budget. |
| Irreversible removal | At most two automated jobs per instance per hour and five globally per day. Apply the lower of operator policy, incident circuit, and these defaults. Manual reviewed operations are also serialized and audited. |
| Verification | Initial read after 5 seconds, then backoff to 15, 30, and 60 seconds, then up to 5 minutes with jitter. Default 30-minute import and 60-minute replacement-grab verification windows. A known running Arr command keeps the case visible without another dispatch. |
| Read failures | Backoff with jitter and respect remote rate limits. Treat auth failures as held until credentials or account state change. Age relevant facts independently. |
| Proposal validity | Default 10 minutes and bound to material evidence, profile and connection revisions. Approval is one-time and any race invalidates the plan. |
| Waiting for replacement | Record a command or new grab only if correlated. An empty result or timeout can exhaust that cycle. An uncertain dispatch stays held and is never interpreted as an empty result. |

Owners can lower limits or explicitly expand a documented, bounded range. Negative, unlimited and ambiguous limit values are invalid. The UI displays budgets, reset times and what would change after an operator action. An operator may acknowledge uncertainty, link upstream proof or cancel further automation. Acknowledgement alone does not establish that an effect was absent. The API must resist stale approvals, double-clicks and replay.

### Circuit breakers

- Trip immediately for an authoritative health failure on a required dependency, verified identity mismatch, corruption in durable state, or a confirmed below-floor capacity observation for a required volume.
- Trip after two distinct jobs exhibit the same corroborated path, permission or post-processing fault in ten minutes within one verified scope. Use exact known scopes for client, Arr instance, media root or mapped volume. Shared-title and shared-clock coincidence are insufficient.
- Trip an action class for three upstream rejections or uncertain writes in ten minutes within one scope. Cap recovery churn across all instances and prevent one release, tracker or broken path from dominating work.
- Distinguish missing capacity telemetry from confirmed low capacity. Show the latest measurement time, service and path namespace. Capacity-dependent writes require positive evidence where the action contract specifies it. Do not infer free space on a remote volume from local container disk usage.
- Import consumes capacity on the library destination when its certified filesystem behavior can allocate space. A replacement search can lead to download, unpack and import allocations on separate volumes. Evaluate every known applicable volume and account for the expected peak footprint and existing reservations. If required capacity, topology or size cannot be bounded, defer automatic allocation-increasing actions, report the exact gap and continue bounded read-only diagnosis. A verified same-volume, no-allocation operation uses its own impact estimate and remaining metadata-space floor.
- On trip, hold affected pending intents before dispatch, reconcile in-flight intents, keep reads active under backoff, and group notification delivery. A storage fault pauses affected writes and searches. Unrelated healthy roots and instances can continue within budget.
- Close soft incidents after two consecutive fresh healthy observations spanning at least two minutes. Identity, uncertain-write, and incompatible contract incidents require documented reconciliation before automation resumes. Resume in staggered order, oldest eligible case first, and rebuild every plan. Manual pause and global kill switch remain effective across restarts.

## 5. Deterministic learning

Learning maintains local operational memory using typed evidence, reproducible rule evaluation and explicit outcomes. It can recognize that a known symptom in the same context usually has a known cause, prioritize a useful probe, preselect a qualified treatment, or identify an incident sooner. It cannot invent a release match, train from raw log text, confer permissions, expand action scope, edit Arr profiles, relax confidence requirements, or enable physical removal. Replaying the same inputs and versioned policy at the same evaluation time yields the same output.

### Pattern identity and data

A fingerprint is an exact versioned tuple of instance UUID, product and adapter semantic epoch, applicable client class and protocol, phase, normalized reason code and ordered corroborating reason set, storage or root identity when causal, and verified structural features such as single file versus pack, unique target mapping, stable completion and upstream import assessment. A treatment family is part of its outcome statistics. Use exact matching and store a canonical serialized form with a local hash for indexing. Title, raw log string, release GUID, path, media names and quality preference are excluded from the fingerprint. Keep a separate deduplication key per verified job generation and treatment with target lineage, preventing duplicated poll observations, retries and repeated imports on the same lineage from inflating confidence.

Store fingerprint, bounded eligible outcome window, outcomes by type, earliest and latest verified timestamps, last match, current state, policy epoch, relevant configuration epochs, probation status and linked redacted sample references. Keep a separate, explicit table for local operator presets. Presets are versioned and reviewable, with exactly the same safety gates as default treatments.

### Eligible observations and confidence

- Training requires a known actor, eligible deterministic plan, stable exact identity, fresh evidence at dispatch, and verified result for all intended effects. An explicit operator approval qualifies only when evidence and action met the same deterministic plan contract. An override or ambiguous external action stays in history as context.
- Import success requires verified target files and compatible history evidence within the verification window, followed by no correlated reversal or deletion within 24 hours. Replacement success requires linked replacement grab and verified library satisfaction within seven days. Cleanup and blocklisting effects have their own verification signals and cannot substitute for media recovery. Incidents use a separate resolved-cause history, requiring positive dependency health and independent job recovery.
- Deduplicate to one qualifying outcome per target lineage per fingerprint and treatment within a rolling 30-day sample window. Promotion requires at least five distinct verified successes across three distinct UTC calendar days, at least 90% success among qualifying outcomes, and zero contradictory safety outcomes. Neutral outcomes such as cancelled work, withdrawn targets and insufficient verification contribute to displayed neutral counts without increasing the confidence denominator.
- A qualifying failed or partial outcome contributes one failure to the relevant treatment window. Any known unintended effect, bad target match, loss of a needed file, or worsening verified quality immediately quarantines the pattern and triggers an incident. Two treatment failures within seven days suspend prioritization. A pattern becomes stale after 30 days without a verified outcome and is eligible again only under the current thresholds.
- Different installations never share learned preferences automatically. Updating Arr or the adapter, changing a relevant root/client/profile mapping, or restoring state across environments starts probation for affected fingerprints. Old outcomes remain auditable. A compatible patch may preserve the semantic epoch only after the integration contract certifies the relevant behavior. An operator can disable learning per instance, inspect evidence, quarantine a fingerprint, and reset its outcome window.
- The engine can prioritize a mature pattern's next read or draft an already-permitted treatment as the recommended action. It reevaluates and logs every safety predicate. All writes remain gated by the configured action mode and current evidence. Holdouts and alternate treatments remain visible. Automatic diagnosis never becomes a release preference or global block rule based on a handful of failures.

### Explainability and replay

Persist evaluation timestamp, policy and adapter revision, matched rules in order, fingerprint revision, success/failure/neutral counts, excluded samples, applicable gates and selected disposition. A user sees explanations such as “The last five verified jobs with this exact post-processing signature needed the same path check. Rescuarr will check that mapping first.” If the matching evidence changes, show what invalidated the prior plan. A replay uses frozen sanitized observations and an explicit policy/learning snapshot. It compares previous and proposed decisions and reports predicted action eligibility, expected impact and rejections. Replay and pattern reset never contact external services or mutate jobs.

## 6. Worked cases

### Sonarr recovers an episode after an unusual filename

At 19:10, Sonarr reports a completed Usenet job and a generic manual-intervention warning. The exact grab references one episode. Arr still sees post-processing, so Rescuarr records the job and waits. After post-processing completes, two consistent scans and a completed grace interval allow an exact manual-import preview. The preview associates one video with the episode and passes the active profile. The adapter certifies the import's source effects for this configuration, and destination capacity is known. The episode has no existing acceptable file or competing grab. The instance's Autonomous policy permits this import class.

Rescuarr reserves the episode, records the intent, re-reads the target and preview, and submits one scoped request. The command acknowledgement starts verification. The case closes when Arr reports the imported file on the expected episode and the import history links it to the job. The separate client data status is displayed only if observable. The case can count toward learning after the observation window. A native Sonarr import occurring during preflight would invalidate the original plan and close the case as externally resolved if the required file is verified.

### A failed Radarr release is replaced within the existing profile

The movie is monitored and has no qualifying file. Radarr identifies the release's stable grab and exact history record. An exact SABnzbd job reports a terminal unrecoverable failure. The only job target is this movie. The download and library roots are healthy, no processing is in progress, capacity is sufficient for a new download, and replacement budgets allow another cycle. The current certified contract can blocklist this specific release and retire the failed job. Rescuarr prefers a path that preserves data where available. If deleting client data is required, execution also requires explicit policy authorization and all dedicated Usenet removal gates.

If the certified adapter suppresses implicit search, Rescuarr verifies the expected retirement and blocklist effects before dispatching a movie-scoped Arr search. Suppose the queue row and SABnzbd job disappear but the blocklist entry fails to appear. The operation becomes partial and the search stays held. If all prerequisites and effects verify, the search can proceed. Arr still chooses the release under the existing profile. The first acceptable new grab starts its own job case linked to the original. Final success requires a verified library import matching the intended movie and constraints. A repeated grab of the failed release is surfaced and consumes its applicable budget.

### A library mount failure affects multiple otherwise healthy jobs

Three completed jobs on one verified root receive new access errors. The integration correlates the errors with that Arr root, and the health check verifies the dependency fault. Rescuarr opens one incident, pauses the related import and replacement writes, and keeps case-specific reads available. Other roots on the same Arr instance continue when their own gates pass. The Prowl message covers the dependency and affected job count once, subject to notification policy. When the mount returns, two healthy observations span the minimum recovery interval. The scheduler rebuilds and staggers plans. A job Arr imported during the incident reconciles as external resolution. A remaining eligible job resumes from the original download.

### A mature pattern encounters new evidence

Five distinct jobs over four days demonstrated the same typed path-mapping diagnosis. Each affected job had an exact root scope, positive mapping correction evidence, and a verified resolution under the same contract. Rescuarr prioritizes checking that mapping for a new job with the same fingerprint. If the new check proves that path access is healthy while Arr reports conflicting identity evidence, the current rule holds the case for review. The historical pattern cannot substitute for current proof. A later adapter upgrade invalidates the fingerprint's epoch and moves it into probation until current evidence qualifies.

## 7. Acceptance scenarios

| Scenario | Required result |
| --- | --- |
| Completed Sonarr download with confirmed grab provenance and exactly one eligible file | Hold through grace, build a current import proposal, execute once in the permitted mode, and verify the mapped episode. Preserve the download unless a separate cleanup plan qualifies. |
| Multiple episodes from one season pack share an exact job ID | Show one case with multiple targets. Deduplicate operations by job. Verify each affected episode. |
| Three valid files and one ambiguous file in a pack | Certified subset import can preserve the valid work. The ambiguous member remains visible and the shared job is protected from automatic removal. |
| Sonarr and Radarr refer to the same client job, or a client ID mapping is unclear | The ownership check holds job-level destruction and explains the conflicting claims. |
| Radarr rejects a release because the existing edition already satisfies its profile | Verify library satisfaction and skip replacement. Keep any queue handling subject to separate, certified effects. |
| A matching-title download is actually a different movie or wrong episode | Evidence is insufficient for automatic import. The UI explains the unresolved identity and preserves the source. |
| A Usenet job has a verified terminal failure and corroborating SABnzbd evidence | When enabled, the exact job can follow a certified blocklist and replacement plan. Verify each requested effect and maintain independent target retry counts. |
| The same download is reported as failed while SABnzbd is still unpacking | Wait and re-evaluate after post-processing. The conflict prevents a terminal failure decision. |
| The NAS mount disappears during several imports | Open a scoped incident, preserve files, and stop retrying affected jobs or searching for replacements. Stagger reassessment after positive health checks. |
| An eligible high-resolution file will exceed the import volume's free-space floor | Hold the import and show the specific capacity source, estimate and minimum. Avoid guessing from another filesystem. |
| A drop in the network occurs immediately after Arr receives an import or remove request | Persist uncertainty across restart, reconcile the actual upstream effects, and avoid re-dispatching the operation. |
| A queue row disappears during pagination | Confirm using coherent reads and targeted evidence. A vanished row alone closes as disappeared without proof or stays held if a write was in flight. |
| The operator changes the quality profile while an approval is open | Expire the plan and recompute eligibility. Preserve the case's previous actions and budgets. |
| Arr search produces no acceptable release | Record the known outcome and cooldown. Respect the per-target cap and surface exhaustion. |
| Arr searches implicitly after a reject request | Follow its history, avoid a duplicate explicit search, and show a successful outcome only after the replacement is verified. |
| A manual import request uses copy mode while Arr can still clean the tracked folder | Refuse automatic execution in the affected preservation-critical scope and retain the preview. |
| A confirmed remove succeeds but a matching blocklist entry cannot be proved | Record the partial operation, hold dependent explicit search, and show the precise missing effect. |
| A separate upgrade candidate is already queued for an existing below-cutoff file | Preserve the existing file and watch the competing candidate. Avoid a redundant recovery search. |
| Learned pattern is repeated across log lines or duplicate jobs on the same lineage | Count qualifying outcomes once. Diagnostic order can change only after the distinct sample and verification requirements are met. |
| Arr is upgraded and response semantics change | Suspend affected writes, mark learned patterns in probation where their epochs changed, and re-enable only validated capabilities. |
| The database is full when an action is prepared or when a response is recorded | Do not dispatch without a durable intent. If the response cannot be saved, reconcile the sending marker after storage recovery before further writes. |
